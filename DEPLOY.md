# Kingdom 2000 — full deployment walkthrough

One linear path from unzip to live site with automatic data. Every step assumes you've done
nothing before it. Total time if you do it all in one sitting: 30–40 minutes, plus a few days
of waiting on things you don't control (a `.eu.org` domain approval, MightPulse indexing your
kingdom if it doesn't already).

**Read this first:** `site/README.md` is the reference copy of everything below, organized by
topic instead of by sequence — use it once the site is live and you're back for a specific
task ("how do I add a KvK cycle", "how do I change the vibe check questions"). This document
is for getting there the first time.

---

## Part 0 — what you're deploying

```
site/
├── index.html, nap.html, kvk.html, alliances.html, applied.html, 404.html   → the pages
├── styles.css                                                              → all styling
├── fit.js       → the placement estimator (power bands, alliance fit)
├── gate.js      → the Discord vibe check (bot filter + etiquette quiz)
├── live.js      → applies data/kingdom.json to the page; degrades silently if absent
├── worker.js    → separate Cloudflare Worker; receives the application form
├── data/kingdom.json        → generated by the API pull below — don't hand-edit
├── config/alliances.json    → hand-maintained fields the API can't know (seats, BT times, etc.)
├── tools/build-data.js      → pulls MightPulse and writes data/kingdom.json
└── .github/workflows/refresh-data.yml   → runs the above daily, unattended
```

Nothing here needs a build step or a framework. It's HTML, CSS and plain JavaScript; the only
tool you need locally is Node, and only for the one-time test in Part 3.

Two moving parts sit outside the `site/` folder once deployed: the Cloudflare Worker (handles
form submissions) and the GitHub Action (pulls fresh data daily). Both are covered below.

## Part 2 — put the code on GitHub

1. github.com → **New repository** → name it `kingdom2000` → **Public** → **Create repository**.
2. On the empty repo page, click **uploading an existing file**.
3. Unzip this package. Drag in **everything inside the `site/` folder** — not the `site` folder
   itself, its contents — including the hidden `.github` folder. If your unzip tool hides
   dot-folders, use `git` from a terminal instead:
   ```bash
   cd site
   git init
   git add -A
   git commit -m "Initial site"
   git branch -M main
   git remote add origin https://github.com/YOUR-USERNAME/kingdom2000.git
   git push -u origin main
   ```
4. Confirm `.github/workflows/refresh-data.yml` shows up in the repo — GitHub will offer to
   run it under the **Actions** tab once it sees it, which is expected; it'll fail until Part 5
   is done, and that's fine.

## Part 3 — get a MightPulse API key and test it locally

Do this before deploying anything, so you know the data pull actually works for your kingdom
before you wire it into a schedule.

1. Go to **api.mightpulse.com** → **Continue with Discord** → **Create API key**. Copy it
   immediately — it's shown once, starts with `kss_`.
2. Check MightPulse has indexed Kingdom 2000: **mightpulse.com/kingdoms** → search `2000`. If
   it's not listed, the API calls in the next step will return 404s — MightPulse only has data
   for kingdoms it tracks, which is most active ones but not guaranteed to be all.
3. Open `config/alliances.json` and check every `"tag"` matches your in-game alliance
   abbreviation **exactly**, including case — tags are case-sensitive and the sample file has
   placeholder tags (`2KVG`, `VLR`, `IRN`, `TSK`, `OBL`) that need to become yours.
4. With Node installed locally:
   ```bash
   cd site
   MIGHTPULSE_KEY=kss_your_key_here node tools/build-data.js
   ```
   You should see it fetch the kingdom, the power board, and each alliance roster in turn,
   then write `data/kingdom.json` and print a summary line. If an alliance 404s, its tag is
   wrong or MightPulse hasn't indexed that roster yet — the script keeps your manual figures
   for that alliance and moves on rather than failing the whole run.
5. Open the new `data/kingdom.json` and sanity-check the numbers against what you see in game.

If this step fails, fix it now — everything downstream assumes this works. If you don't have
Node locally and don't want to install it, skip to Part 5 and let GitHub Actions run it for you
in the cloud; the log there tells you the same thing.

## Part 4 — set the Discord invite and the webhook

Two separate Discord integrations. Do both now while you're in the Discord settings anyway.

### 4a. The permanent invite (for the vibe-check gate)

1. Your Discord server → server name → **Invite People** → **Edit invite link**.
2. Set **Expire after: Never** and **Max uses: No limit**. The default invite expires in 7
   days — skip this and the button quietly starts sending people to a dead link.
3. Copy the code after `discord.gg/` — just the code, not the full URL.
4. Open a browser console (F12 → Console tab) anywhere, and run:
   ```js
   btoa("YourInviteCode".split("").reverse().join(""))
   ```
5. Open `site/gate.js`, find `INVITE_ENC`, and replace its value with the result.

This is a speed bump against scrapers and page-source skimmers, not a lock — anyone with a
console can decode it in ten seconds. That's fine; it isn't meant to do more than that.

### 4b. The application-form webhook

1. Your officers' channel → gear icon → **Integrations** → **Webhooks** → **New Webhook** →
   **Copy Webhook URL**. Treat it like a password.
2. Keep this URL handy — it goes into the Cloudflare Worker in Part 6, not into any file here.

## Part 5 — deploy the site to Cloudflare Pages

1. dash.cloudflare.com → **Workers & Pages** → **Create** → **Pages** tab → **Connect to Git**.
2. Authorize GitHub, pick the `kingdom2000` repo.
3. Build settings: **Framework preset: None**. **Build command:** leave blank — delete
   anything Cloudflare pre-fills. **Build output directory:** `/`. There is nothing to compile.
4. **Save and Deploy.** After about a minute you're live at `kingdom2000.pages.dev`.

From now on, every `git push` (or GitHub web edit) redeploys automatically in well under a
minute.

---

## Part 6 — turn on the daily data refresh

1. GitHub repo → **Settings** → **Secrets and variables** → **Actions** → **New repository
   secret**. Name: `MIGHTPULSE_KEY`. Value: your key from Part 3.
2. Repo → **Actions** tab → **Refresh kingdom data** (should already be listed) → **Run
   workflow** → **Run workflow**. Watch it go green.
3. Check the commit it made — `data/kingdom.json` should show fresh timestamps. Cloudflare
   Pages redeploys automatically off that commit.
4. It now runs itself at 05:00 UTC daily. Nothing further to do unless you change alliance
   tags later — if you do, update `config/alliances.json` and push.

---

## Part 7 — deploy the application-form Worker

This is a second, separate thing in Cloudflare from the Pages site — a small serverless
function, not a page.

1. dash.cloudflare.com → **Workers & Pages** → **Create** → **Workers** tab → name it
   `kingdom2000-apply` → **Deploy** the starter, then **Edit code**.
2. Delete the starter code, paste in the full contents of `site/worker.js`, **Deploy**.
3. Worker → **Settings** → **Variables and Secrets** → **Add**:
   - `DISCORD_WEBHOOK` — type **Secret** — the webhook URL from Part 4b
   - `SITE_ORIGIN` — type **Text** — `https://kingdom2000.pages.dev`
4. **Deploy** again — variables don't take effect until you redeploy.
5. Copy the Worker's URL from its overview page (`https://kingdom2000-apply.something.workers.dev`).
6. In `index.html`, find `YOURNAME` inside the `<form action="...">` line and replace the
   whole placeholder URL with your real one. Commit and push.

Optional flood guard: **Storage & Databases** → **KV** → create a namespace → Worker →
**Settings** → **Bindings** → bind it as `RATE`. Limits one submission per IP per minute.

## Part 8 — test the whole thing end to end

Before you post the link anywhere:

1. Open `kingdom2000.pages.dev` on your phone and on desktop.
2. Scroll to **Where would you land?** — enter a power figure, confirm it returns a sensible
   rank per alliance.
3. Scroll to **Vibe check** — answer the arithmetic question correctly and all ten quiz
   questions honestly, submit, confirm the Discord button appears and the link works.
4. Answer the quiz wrong on purpose — confirm you get the explanation screen and a working
   **Try again**.
5. Fill in the application form with junk test data, submit — confirm it lands in your Discord
   officers' channel as an embed, and that you land on the confirmation page.
6. Check the footer stamp under the leaderboard — it should say figures were refreshed today,
   from MightPulse.

If the form doesn't reach Discord: the webhook secret is wrong, or the Worker wasn't
redeployed after adding it. If the leaderboard shows placeholder-looking numbers: the data
refresh hasn't run yet, or an alliance tag doesn't match — check the Actions log.

## Part 9 — free domain (optional, do in parallel with everything above)

`kingdom2000.pages.dev` works immediately and never needs this step. If you want a shorter,
non-`.dev` address:

1. Apply at **eu.org** for `kingdom2000.eu.org` — the only real domain still free, forever.
   Volunteer-reviewed, can take days to weeks. Submit it now; check back later.
2. If granted: Cloudflare Pages project → **Custom domains** → **Set up a custom domain** →
   follow the DNS instructions eu.org gives you.
3. Keep `kingdom2000.pages.dev` working as a permanent alias so old Discord links never break.

## Part 10 — what's automatic now, and what still needs a human

| Updates itself | Still manual |
|---|---|
| Kingdom age, active governor count | KvK results and cycle notes |
| Alliance power, member counts, rank | The NAP text and amendment dates |
| Top-100 and top-10 power floors | King buff schedule |
| Placement-estimator power bands | Event times |
| Alliance leaderboard | Open seats, Bear Trap slots, spending mix |
| | Castle crowns |
| | Community schedule |

The manual list lives in the HTML files directly, plus `config/alliances.json` for the fields
attached to a specific alliance. `site/README.md` has a table of exactly which file and which
tag to search for, per item.

**Read the "dependency risk" section of `site/README.md` before you treat the automated column
as permanent** — the data source is an unofficial, unaffiliated fan API, not something Century
Games runs or guarantees, and the site is built to keep working with stale manual figures if it
ever goes away. That's a feature, not a bug, but it means someone should notice if the "Figures
last updated" stamp stops moving.

## If something breaks

- **Site shows old data forever:** GitHub → Actions tab → check the last run of *Refresh
  kingdom data* for an error. Common cause: an alliance tag in `config/alliances.json` no
  longer matches the in-game abbreviation.
- **Form doesn't post to Discord:** Worker → check `DISCORD_WEBHOOK` is set and the Worker was
  redeployed after setting it. Test the webhook URL directly by posting to it with `curl`.
- **Discord button goes nowhere / decodes wrong:** re-run the `btoa(...)` snippet in Part 4a
  and make sure you copied the whole output into `INVITE_ENC`.
- **Pages didn't redeploy after a commit:** Cloudflare Pages project → **Deployments** tab —
  check it's still connected to the right branch.
